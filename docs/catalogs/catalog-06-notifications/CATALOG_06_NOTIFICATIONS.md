# PART II — DESIGN PRINCIPLES

## 2. Core Principles

### `NOTIFY-PRINCIPLE-001 — Timely`

Notifications must be issued close enough to the triggering event to remain operationally useful.

### `NOTIFY-PRINCIPLE-002 — Actionable`

Notifications should communicate a meaningful condition or required next action.

### `NOTIFY-PRINCIPLE-003 — Relevant`

Recipients are determined by business rules, not client input.

### `NOTIFY-PRINCIPLE-004 — Privacy-Aware`

Notifications must never expose confidential information to unauthorized recipients.

### `NOTIFY-PRINCIPLE-005 — Deduplicated`

Repeated identical events should be grouped when the cataloged policy allows.

### `NOTIFY-PRINCIPLE-006 — Traceable`

Every notification maps to cataloged triggers, audit hooks, and related governance artifacts.

### `NOTIFY-PRINCIPLE-007 — Accessible`

In-app notifications must support accessible presentation and interaction.

### `NOTIFY-PRINCIPLE-008 — Authorization Intact`

Priority and delivery never replace Catalog 5 authorization.

### `NOTIFY-PRINCIPLE-009 — Fail Closed on Privacy`

When recipient eligibility is unclear, detailed content is withheld.

### `NOTIFY-PRINCIPLE-010 — Catalog Authority`

No production notification name may exist outside this catalog or an approved amendment.

Notifications should be:

* timely
* actionable
* relevant
* privacy-aware
* deduplicated
* traceable
* accessible

# PART VIII — DEDUPLICATION

Notifications generated by repeated identical events should be grouped when appropriate.

Deduplication keys may include:

* notification type
* resource
* recipient
* time window

Security notifications are generally not deduplicated.

| Dedup Policy ID | Policy |
| --- | --- |
| DEDUP-001 | Group identical type + resource + recipient within time window |
| DEDUP-002 | No deduplication (security and other explicit exceptions) |

# PART XVI — LOCKED NOTIFICATION DECISIONS

## Locked Decisions

1. No production notification type may exist outside this catalog or an approved amendment.
2. Recipients are determined by business rules, not client input.
3. Priority never replaces authorization.
4. Notifications must never expose confidential information to unauthorized recipients.
5. Security notifications are generally not deduplicated.
6. Reading a notification does not necessarily acknowledge it.
7. Future channels (SMS, PUSH, WEBHOOK) require formal catalog amendment before production use.
8. Acknowledgment-required notifications must be auditable where required.
9. Seeded notification names in this catalog are authoritative permanent identifiers.
10. Notifications must remain accessible without relying solely on color for priority.
11. Deduplication must not suppress SECURITY_EVENT by default.
12. Configuration-change and security notifications require acknowledgment.
13. Notification delivery failures must not silently alter business state.
14. Exact channel enablement may be environment-specific but must use cataloged notification types.
15. Additional notification types require catalog amendment under this contract.
